# Harness 工程的原则与理由

来源：一个单人 + Claude Code/Codex 开发的纯本地项目（20+ 份计划、400+ commit）的实践总结。
每条写"做法 → 为什么 → 实践中学到的"。

## 1. AGENTS.md 是地图，不是手册

- **做法**：`AGENTS.md` ~100 行，只有：项目一句话、每次会话开始时的步骤、常用命令表、文档索引、红线、工作约定。`CLAUDE.md` 只有一行 `@AGENTS.md`，让 Claude Code 和 Codex 读同一份。
- **为什么**：入口每次会话都会被加载，越长越稀释注意力；细节放 `docs/` 按需读。
- **学到的**：用 `check_docs.py` 硬性限制行数（120），否则会悄悄膨胀。新增内容"优先写进对应文档，这里只加链接"。

## 2. 每次会话开始的固定动作

读 AGENTS.md → 读 SOP 确认阶段 → 读 `plans/active/` 的「进度」「下一步」→ 读 TODO → 跑 `make check` 确认基线为绿 → 从「下一步」继续。
- **为什么**：AI 没有跨会话记忆，固定的启动序列让任何新会话 5 分钟内接上工作。
- **基线不绿先处理**，否则后面所有"我改完 make check 绿了"的结论都不可信。

## 3. 人只在三个关口介入

设计批准、计划批准、里程碑验收。其余由 AI 自主，但遇到**升级条件**必须停下来问：
设计矛盾/不可行、需要计划外依赖或公共接口改动、风险验证结论与预期不符、同一问题三种修法都失败、破坏性操作、范围变化、需要付费 key。
- **"批准"必须明确**：沉默、"先这样吧"、只同意想法都不算；批准只对当时那份产出有效。
- 不属于升级条件的问题 AI 自己判断，**理由写进计划的「决策记录」**——人事后可审计，而不是事前被打扰。
- **学到的**：负责人常常一行话批准计划同时改一个决定，所以有争议的决定要以"草稿"写进决策记录并在汇报里点出来。

## 4. 计划文件就是交接文件

- 必需章节：元信息、目标、范围（包含/不包含）、验收标准、任务、进度、下一步、决策记录、意外与发现、阻塞、验证记录。暂时没有就写"无"，由脚本检查。
- 任务 1–3 小时，结束时 `make check` 为绿；**代码和计划更新放同一个 commit**。
- 计划只写结构和意图（文件、接口签名、验收标准、验证命令），不写完整实现。
- 「下一步」写成可执行指令："实现 `x.py` 的 `rollback()`，测试 `test_rollback_*` 已写、目前失败"，而不是"继续做快照"。
- **计划文件永远要能让一个全新的会话接着干。** 不把关键信息只留在对话里。
- 同一时间 `active/` 只放一份计划（脚本给警告）。

## 5. `make check` 是唯一质量关口

- 一个命令覆盖：lint、格式、类型检查、测试、架构分层契约、文档检查。合并前必须全绿；pre-commit 跑快速子集 `check-fast`。
- 不用 skip/xfail/`type: ignore`/`noqa` 绕过失败，除非计划里写明理由。
- 慢测试和需要真实 key 的冒烟测试（`make smoke`）不进默认关口，但要有独立命令和运行说明。
- **学到的**：
  - Makefile 里主动定位工具路径（沙箱的 PATH 可能缺 `~/.local/bin`、nvm shims）。
  - 子目录还没创建时自动跳过对应检查（`$(wildcard backend/pyproject.toml)`），让脚手架从第一天起就是绿的。
  - 冒烟测试用 `env -i` + 白名单环境变量运行，防止宿主（如 Claude Code）注入的变量污染用例。
  - 合并前的 `make check` 要在**合并后的代码**上跑。

## 6. 文字约定要逐步变成机器检查

- SOP 里有一条触发器："一条文字约定被反复违反 → 把它改成 lint 规则或结构测试，并删掉相应文字"。
- 已机器化的例子：文档相对链接有效、计划/ADR 必需章节、ADR 编号唯一、AGENTS.md 行数、技术债编号不撞号、模块分层（import-linter）、红线目录禁写（Claude Code `permissions.deny`）。
- 见 [mechanization.md](mechanization.md)。

## 7. 架构分层写成可执行契约

- `docs/ARCHITECTURE.md` 写模块表（职责 / 可以依赖谁）和依赖方向；同样的规则写进依赖检查工具的配置，由 `make check` 强制。
- 新建模块时同时补契约；ARCHITECTURE.md 必须和代码一致（收尾清单检查）。
- **学到的**：契约名写成人话加规则编号（"agent 不 import stages（规则 2）"），失败信息本身就是文档。

## 8. 外部 SDK 知识以 `references/` 为准

- 训练知识可能过时。遇到没记录的行为：查官方文档或实测 → 写进 `references/<库>.md`，每条标 ✅ 已验证 / ⚠️ 待验证 / ❌ 已否定，注明日期和来源。
- 过期就原地更新并改日期，不追加矛盾的新记录；❌ 记录保留，防止以后再误用。
- **学到的**：这是收益最高的一类文档——新会话不再重复踩同一个 SDK 坑。spike（技术验证）结论也写在这里。

## 9. 决定、债务、质量各有登记处

| 文件 | 写什么 | 何时写 |
|---|---|---|
| `decisions/NNNN-*.md`（ADR） | 背景、决定、考虑过的其他方案、影响 | 选择影响超出当前计划时 |
| `quality/tech-debt.md` | TD-N：位置、问题、影响、建议处理、来源；处理完移到「已处理」 | 发现暂不处理的问题时（评审发现尤其多） |
| `quality/QUALITY.md` | 每模块 A/B/C 评级 + 已知缺口 | 每个里程碑收尾 |
| `plans/TODO.md` | 还没写成计划的事，P0/P1/P2；优先级由人定 | 发现计划外事项时 |
| `glossary.md` | 领域术语 | 出现新术语时 |

- **学到的**：定期开"技术债清理"计划（按领域挑一批有真实影响、改动小的 TD），比零散修更有效；登记表条目要核对是否已过时再处理。

## 10. 自验证要有分级证据

- L1 `make check` → L2 针对性测试/假运行时端到端 → L3 curl 运行中的服务 → L4 浏览器操作截图 → L5 真实模型/真实 key 冒烟。
- 每条验收标准在「验证记录」里写命令、输出摘要、结论；证据文件放 `data/evidence/<计划 id>/`（不进 git）。验证不了写"未验证"+原因，不能写"通过"。
- **学到的**：jsdom/单测看不出布局问题，界面改动一定要 L4；用隔离端口和临时数据目录做走查，不碰真实数据；能用本机订阅登录跑真实模型就优先用（不产生 API 费用）。

## 11. 评审者不能是作者

- 评审由新会话或 subagent 做，不能是写这段代码的上下文。分支收尾前做一次全分支独立评审，发现逐条处理：修复，或写明理由后不改（并登记 TD）。
- **学到的**：独立评审多次发现单测漏掉的真实问题（例如安全绕过）。

## 12. 分支与合并

- 每份计划一个分支（推荐独立 worktree）；每任务至少一个 commit，格式 `<type>(<scope>): <说明>`。
- 人验收后 rebase 到最新 main，在合并后代码上跑完整 `make check`，`--no-ff` 合并。不 force push，不改写 main 历史。
- **快速通道**：≤3 个文件、不改公共接口、无新依赖、不涉及设计决定 → 人在对话里同意后直接做（仍先写测试），commit 说明写清原因；中途发现不满足就改走完整流程。

## 13. 红线写成绝对规则

AGENTS.md 的红线是"违反就停下来问人"的硬规则，例如：不改旧项目、不削弱 `make check`、不引入计划外依赖/公共接口、不改已批准的设计、运行时数据目录不进 git 也不在热重载监听范围内。能用工具权限挡住的（如 `.claude/settings.json` 的 `permissions.deny`）就挡住。
